# 系统长期运行内存暴增与自动退出（OOM）根治与优化计划

针对程序在连续运行数小时后出现内存不断上涨、最终触发 Node.js / 浏览器 OOM（内存溢出）自动退出的问题，本方案进行了全链路的内存排查与深度定位，并制定了完整的系统级内存治理与自动回收计划。

---

> [!IMPORTANT]
> **代码锁定与安全准则（Code Lock Compliance）**：
> 本方案仅针对数据缓存、内存存储与 GC 回收机制进行优化治理，**严禁且绝不触碰** List 1~List 4 固化锁定模块的核心策略算法、均线发散规则、5K 爆发推进逻辑以及对冲解套/止盈止损计算。

---

## 1. 内存暴增与自动退出的核心根因诊断

通过对系统全路径代码及内存分布的排查，定位到以下 4 个造成内存泄漏与堆积的主要环节：

### 核心泄漏点 1：`klineMultiTfStore` 多周期 K 线共享池只增不减
* **问题现象**：每当扫描器或行情长连接获取各币种多周期（15m, 1h, 4h, 1d）K 线数据时，数据会被写入 `window.KLINE_MULTI_TF_CACHE` 与内部 `memoryMap` 中。
* **根因**：没有限制单个 Map 的容量上限，也没有对过期或离开扫描列表的币种进行剪枝。随着上百个币种持续轮询， Map 内部累积数万条 K 线对象，导致内存线性飙升。

### 核心泄漏点 2：全局 `window.KLINE_LIMIT_CACHE` 与日线缓存堆积
* **问题现象**：`klineDailyStore` 在拉取 1d 日线数据时，会将全量日线挂载在全局 `window.KLINE_LIMIT_CACHE` 下。
* **根因**：全局对象缺少定时清理与容量阈值，运行数小时后占用数百 MB 堆内存。

### 核心泄漏点 3：List 2 `klineStoreRef` 环形缓冲区无限扩展
* **问题现象**：List 2（大十字星与均线发散监控）中的 `klineStoreRef.current` 在更新 WebSocket 实时 K 线时，将所有出现过的币种持续保存在内存 Map 中。
* **根因**：没有根据当前活性候选池对旧币种进行清理，导致 Map 规模无上限增加。

### 核心泄漏点 4：Node.js 默认堆内存限制 (Heap Limit) 与对象频发克隆
* **问题现象**：Node.js 默认 Old Space 堆上限约为 1.5GB ~ 2GB。一旦高频轮询产生的临时对象未能被及时 GC 释放，即触发 `FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory` 导致进程自动崩溃退出。
* **根因**：`priceRegistry.ts` 等高频模块在获取全量价格时使用对象展开运算符（`...`）频繁复制大对象，加剧了垃圾回收（GC）的延迟与内存碎片化。

## 2. 详细完整解决计划与架构方案

为彻底解决内存暴增与程序退出问题，系统将采取 **“前端主动剪枝 + 后端堆扩展 + 全局定时清扫 + 高频垃圾减排”** 四维一体的治理计划：

```
┌────────────────────────────────────────────────────────────────────────┐
│                        系统内存治理与自动回收架构                     │
└────────────────────────────────────────────────────────────────────────┘
                                   │
         ┌─────────────────────────┼─────────────────────────┐
         ▼                         ▼                         ▼
┌──────────────────┐      ┌──────────────────┐      ┌──────────────────┐
│ 1. 数据存储剪枝  │      │ 2. 全局定时清扫  │      │ 3. 内存堆扩容    │
│  (Store Pruning) │      │ (Global Sweeper) │      │  (Node Heap Ex)  │
└──────────────────┘      └──────────────────┘      └──────────────────┘
  - 单 Key 限 300 根       - 定时清扫旧 Cache         - 堆上限扩展至 4GB
  - Map 容额上限 500       - 联动 CacheManager        - 开启手动 GC 暴露
  - 非候选币实时淘汰       - 一键释放图表内存         - 后端 API 缓存截断
                                   │
                                   ▼
                          ┌──────────────────┐
                          │ 4. 高频垃圾减排  │
                          │ (GC Optimizations│
                          └──────────────────┘
                            - 移除无谓对象展开
                            - 共享浅拷贝或弱引用
```

### 实施细节 1：`klineMultiTfStore` 内存容量保护与动态剪枝
1. **单条 K 线数据截断**：将所有存储的 K 线限制为最新 **300 根**，抛弃历史无用数据。
2. **容量保护器（Capacity Sweeper）**：当 `memoryMap` 或 `winCache` 大小超过 **500 个 Key** 时，触发淘汰机制，优先清除时间戳最旧或未在当前活跃监控列表中的币种数据。

### 实施细节 2：`klineDailyStore` 定时内存清扫器 (`purgeStaleMemoryCache`)
1. 增加 `purgeStaleMemoryCache()` 接口，在清理时自动清空 `window.KLINE_LIMIT_CACHE` 中的失效缓存。
2. 当日线 Map 大小超过 **300 项** 时，自动清除超过 30 分钟未更新的旧币种日线。

### 实施细节 3：List 2 / List 3 / List 4 局部存储器（StoreRef）动态剪枝
1. 在 `useGrandCrossing.ts` 中监控 `klineStoreRef.current` 的容量，一旦超过 **600 项**，主动踢出既不属于启动池、也不属于 List 2 候选池的淘汰币种。
2. 在 `useMomentumAudit.ts` 与 `useStructureAudit.ts` 中，为历史信号与计算缓存设立 **2 小时生存期（TTL）**，定期清理过期锁。

### 实施细节 4：全局 CacheManager 与手动/自动一键内存释放
1. 将 `klineMultiTfStore.purgeStaleEntries()` 和 `klineDailyStore.purgeStaleMemoryCache()` 统一注册到系统 `CacheManager` 中。
2. 用户点击系统面板“清除缓存”或系统检测到内存压力时，一键同步释放所有前端 DOM 与内存缓存。

### 实施细节 5：后端 Node.js 启动参数与服务器缓存优化
1. **堆内存扩展**：在启动脚本加入 `--max-old-space-size=4096 --expose-gc` 参数，将最大可用堆从 1.5G 提升至 **4GB**。
2. **服务端缓存截断**：将 `server.ts` 中的 `serverCache` 限制为最多 **100 个 Key**，对高频行情代理响应进行 LRU 自动覆盖，防止后端 Node 堆积。

### 实施细节 6：`priceRegistry` 高频读取零垃圾优化
1. 优化 `priceRegistry.ts` 中的 `getAllPrices()` 方法，避免每次高频调用都使用 `{ ...map }` 创建全新对象。
2. 改用只读引用或批量变更时更新版本号的方式，显著降低 V8 垃圾回收器（GC）的暂停时间和内存开销。

## 3. 验证与上线排查方案

1. **静态编译检查**：运行 `compile_applet` 确保无类型错误与破坏性改动。
2. **内存监控面板对接**：在系统性能监视模块 (`modules/system-monitor/`) 中查看堆内存 (`heapUsed`) 是否在 200MB ~ 500MB 区间内平稳波动，不再呈现无限制直线飙升。
3. **长期稳定运行测试**：验证系统在连续轮询 10+ 小时后，内存自动收敛并维持在安全线以下，彻底消除程序无故退出现象。
